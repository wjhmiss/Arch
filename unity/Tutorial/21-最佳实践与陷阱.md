## 21.2 组件设计原则

### 21.2.1 使用 struct 而非 class

Arch 的组件可以是 struct 或 class，但**强烈推荐 struct**。原因：

| 维度 | struct | class |
|------|--------|-------|
| 内存布局 | 连续存储在 Chunk 中 | 堆分配 + 引用，破坏局部性 |
| GC 压力 | 零 | 每个实例都进堆 |
| 拷贝语义 | 值类型，无别名问题 | 引用语义，可能被多持有 |
| 装箱开销 | 仅在 `GetAllComponents()` 时 | 始终引用 |

```csharp
// ❌ 错误：使用 class
public class Health { public int Value; }

// ✅ 正确：使用 struct
public struct Health { public int Value; }
```

🔥 Arch 的 Chunk 按 ComponentType 字节数布局，struct 让数据连续紧凑存储，缓存命中率显著高于 class。

### 21.2.2 组件保持小而专注

每个组件应只表达**一个数据维度**。不要把多个概念塞进一个 struct：

```csharp
// ❌ 错误：组件过大，包含多个职责
public struct Character
{
    public float Health;
    public float Mana;
    public float Stamina;
    public Vector3 Position;
    public Vector3 Velocity;
    public int Level;
    public int Experience;
    public string Name;  // 引用类型！
}

// ✅ 正确：拆分小而专注的组件
public struct Health { public float Value; }
public struct Mana { public float Value; }
public struct Position { public float X, Y, Z; }
public struct Velocity { public float X, Y, Z; }
public struct Level { public int Value; }
public struct Experience { public int Value; }
```

💡 拆分后可以独立查询：只要 Health 的系统不需要读 Velocity。如果都塞进一个 struct，每次查询都要加载所有字段。

### 21.2.3 避免引用类型字段

struct 中包含引用类型字段（如 `string`、`object[]`、`List<T>`）会带来两个问题：

1. **GC 压力**：引用类型实例在堆上
2. **缓存局部性被破坏**：跳转到堆地址访问数据

```csharp
// ❌ 错误：包含 string
public struct Enemy
{
    public string Name;     // 每个实体一份 string
    public int[] Skills;    // 每个实体一份 int[]
}

// ✅ 正确：使用 int 索引到全局表
public struct Enemy
{
    public int NameId;     // 索引到全局 string 表
    public int SkillCount;
    public int FirstSkillId;  // 索引到全局 Skill 数组
}
```

⚠️ 如果**必须**使用引用类型字段，请评估是否真的需要 ECS——有些数据本就不适合 struct 化（如配置对象）。

### 21.2.4 使用 record struct 获得自动 Equals

`record struct`（C# 10+）会自动生成 `Equals`、`GetHashCode`、`ToString`，便于比较、字典存储、调试输出：

```csharp
// ✅ 推荐：record struct
public readonly record struct Position(float X, float Y, float Z);

// 使用
var p1 = new Position(1, 2, 3);
var p2 = new Position(1, 2, 3);
Console.WriteLine(p1 == p2);  // True，自动 Equals
```

📖 详见 [Arch.Docs 的事件示例](file:///d:/Unity/Arch/unity/Tutorial/19-Arch.EventBus事件总线.md#L211) 中广泛使用 `record struct` 作为事件。

## 21.3 系统设计原则

### 21.3.1 单一职责

每个系统只做一件事：

```csharp
// ❌ 错误：一个系统什么都做
public class GameLogicSystem : BaseSystem<World, float>
{
    public override void Update(in float t)
    {
        Move();
        Combat();
        Spawn();
        Despawn();
        UpdateUI();
    }
}

// ✅ 正确：每个系统专注一个职责
public class MovementSystem : BaseSystem<World, float> { /* ... */ }
public class CombatSystem : BaseSystem<World, float> { /* ... */ }
public class SpawnSystem : BaseSystem<World, float> { /* ... */ }
public class DespawnSystem : BaseSystem<World, float> { /* ... */ }
```

📖 详见 [第14章 Arch.System](14-Arch.System系统框架.md) 中 `Group<float>` 的组合方式。

### 21.3.2 避免在系统中持有状态

系统应该是**无状态**的逻辑单元——状态全部存在组件里。系统内部字段只放**只读配置**：

```csharp
// ❌ 错误：在系统中持有运行时状态
public class CounterSystem : BaseSystem<World, float>
{
    private int _counter = 0;  // 跨帧状态

    public override void Update(in float t)
    {
        _counter++;  // 不可重入，难以并行
    }
}

// ✅ 正确：把状态放到组件里
public struct Counter { public int Value; }

[Query]
public void Tick(ref Counter c) => c.Value++;
```

### 21.3.3 使用 World.SharedJobScheduler 并行

[World.cs#L107](file:///d:/Unity/Arch/Arch/src/Arch/Core/World.cs#L107) 提供了静态共享 JobScheduler：

```csharp
public static JobScheduler? SharedJobScheduler { get; set; }
```

初始化一次即可全局复用：

```csharp
private void Awake()
{
    World.SharedJobScheduler = new JobScheduler(
        maxJobs: Environment.ProcessorCount);
    _world = World.Create();
}
```

使用并行查询：

```csharp
_world.ParallelQuery(in query, (ref Position p, ref Velocity v) =>
{
    p.X += v.X * dt;
});
```

📖 并行查询实现见 [World.Jobs.cs#L35](file:///d:/Unity/Arch/Arch/src/Arch/Core/Jobs/World.Jobs.cs#L35)。详见 [第11章 多线程与 Jobs](11-多线程与Jobs.md)。

## 21.4 查询优化

### 21.4.1 缓存 QueryDescription

`QueryDescription` 构造时会计算组件签名的 hash。如果每次 `Update` 都 `new` 一次，会反复计算：

```csharp
// ❌ 错误：每帧新建 QueryDescription
private void Update()
{
    var query = new QueryDescription().WithAll<Position, Velocity>();
    _world.Query(in query, ...);  // 每帧重新计算签名
}

// ✅ 正确：缓存为 static readonly
private static readonly QueryDescription _moveQuery =
    new QueryDescription().WithAll<Position, Velocity>();

private void Update()
{
    _world.Query(in _moveQuery, ...);
}
```

📖 World 内部还有 `QueryCache` 字典缓存（[World.cs#L203](file:///d:/Unity/Arch/Arch/src/Arch/Core/World.cs#L203)），缓存 QueryDescription 后命中率最高。

### 21.4.2 使用 IForEach 结构体内联

Lambda 委托会引发装箱与 GC 分配。使用 `IForEach` 结构体可以让 JIT 内联：

```csharp
// ❌ 慢：委托 + 闭包
public struct JobData { public float Dt; }
private JobData _data;

private void Update()
{
    _world.Query(in query, (ref Position p, ref Velocity v) =>
    {
        p.X += v.X * _data.Dt;  // 闭包捕获 this
    });
}

// ✅ 快：IForEach 结构体
public struct MoveJob : IForEach
{
    public float Dt;
    public void Update(Entity e) { /* 通过 e.Get 访问组件 */ }
}

private MoveJob _job;
private void Update()
{
    _job.Dt = Time.deltaTime;
    _world.InlineQuery<MoveJob>(in _query);
}
```

📖 `InlineQuery<T>` 的实现见 [World.cs#L778](file:///d:/Unity/Arch/Arch/src/Arch/Core/World.cs#L778)。详见 [第8章 Query 查询系统](08-Query查询系统源码解析.md) 与 [第12章 批量操作](12-批量与批量操作.md)。

### 21.4.3 合理使用 WithNone 过滤

`WithNone` 可以减少匹配实体数：

```csharp
// ❌ 在回调里 if 判断
_world.Query(in query, (ref Dead dead, ref Health h) =>
{
    if (dead.Value) return;  // 浪费
    h.Value -= 1;
});

// ✅ 用 WithNone 排除
var query = new QueryDescription()
    .WithAll<Health>()
    .WithNone<Dead>();

_world.Query(in query, (ref Health h) => h.Value -= 1);
```

🔥 World 在 Query 阶段就按 Signature 过滤 Archetype，`WithNone` 能跳过整个 Archetype 的 Chunk，远比回调内 `if` 高效。

## 21.5 内存管理陷阱

### 21.5.1 World 必须 Dispose

[World.cs#L539](file:///d:/Unity/Arch/Arch/src/Arch/Core/World.cs#L539) 的 `Dispose` 是 `IDisposable` 实现：

```csharp
[StructuralChange]
public void Dispose()
{
    Dispose(true);
    GC.SuppressFinalize(this);
}
```

⚠️ 不 Dispose 会导致：

1. `World.Worlds` 静态数组残留 null 引用
2. Chunk 数组等非托管资源无法及时回收
3. `WorldSize` 计数错误

```csharp
// ✅ 正确：使用 using 或 try-finally
using var world = World.Create();
// ... 业务逻辑

// ✅ 在 MonoBehaviour 中
private void OnApplicationQuit() => _world?.Dispose();
```

### 21.5.2 不要在 Query 回调中创建 World

```csharp
// ❌ 错误：在回调中创建 World
_world.Query(in query, (Entity e) =>
{
    var newWorld = World.Create();  // 每个实体一次！灾难
});

// ✅ 正确：World 在启动时创建一次
private void Awake() => _world = World.Create();
```

🔥 World 创建会触发**全局静态数组扩容**（`World._worlds`，[World.cs#L81](file:///d:/Unity/Arch/Arch/src/Arch/Core/World.cs#L81)），还会加锁 `WorldsLock`（[World.cs#L90](file:///d:/Unity/Arch/Arch/src/Arch/Core/World.cs#L90)）。在 Query 回调里创建会引发死锁与严重性能问题。

### 21.5.3 警惕闭包分配

Lambda 捕获局部变量会生成隐藏类与堆分配：

```csharp
// ❌ 闭包分配
private void Update()
{
    float dt = Time.deltaTime;
    _world.Query(in query, (ref Position p, ref Velocity v) =>
    {
        p.X += v.X * dt;  // dt 被捕获，每次 Query 都 new 一个闭包对象
    });
}

// ✅ 使用 IForEach 结构体字段
private struct MoveJob : IForEach
{
    public float Dt;
    public void Update(Entity e) { /* ... */ }
}
```

### 21.5.4 GetAllComponents 会装箱

[EntityExtensions.cs#L60](file:///d:/Unity/Arch/Arch/src/Arch/Core/Extensions/EntityExtensions.cs#L60)：

```csharp
public static object?[] GetAllComponents(this in Entity entity)
```

返回 `object?[]`，所有 struct 组件都会被装箱。**只在调试时使用**，不要在主循环调用。

```csharp
// ❌ 主循环中调用
foreach (var e in entities)
{
    var comps = e.GetAllComponents();  // 装箱地狱
    foreach (var c in comps) { /* ... */ }
}

// ✅ 用具体类型的 Query
_world.Query(in query, (ref Health h) => { /* ... */ });
```

## 21.6 线程安全陷阱

### 21.6.1 结构变更必须单线程

**结构变更**（创建/销毁实体、增删组件）会修改 Archetype 与 Chunk，**绝不能在 ParallelQuery 回调中执行**：

```csharp
// ❌ 错误：在并行回调中销毁实体
_world.ParallelQuery(in query, (Entity e) =>
{
    if (e.Get<Health>().Value <= 0)
        e.Destroy();  // 数据竞争，崩溃！
});
```

📖 [World.Jobs.cs#L30](file:///d:/Unity/Arch/Arch/src/Arch/Core/Jobs/World.Jobs.cs#L30) 注释明确写道：`NOT thread-safe! Do not call a parallel query from anything but the main thread!`

### 21.6.2 并行查询中使用 CommandBuffer

需要在并行回调中做结构变更时，使用 [CommandBuffer](file:///d:/Unity/Arch/Arch/src/Arch/Buffer/CommandBuffer.cs)：

```csharp
var buffer = new CommandBuffer();

_world.ParallelQuery(in query, (Entity e) =>
{
    if (e.Get<Health>().Value <= 0)
    {
        buffer.Destroy(e);  // 不立即执行，安全
    }
});

// 主线程回放
buffer.Playback(_world);
```

📖 CommandBuffer 的实现位于 [Arch/Buffer/CommandBuffer.cs](file:///d:/Unity/Arch/Arch/src/Arch/Buffer/CommandBuffer.cs)，详见 [第10章 CommandBuffer 命令缓冲](10-CommandBuffer命令缓冲.md)。

## 21.7 常见错误代码与修复

### 21.7.1 使用已销毁的 Entity

```csharp
// ❌ 错误
_world.Destroy(entity);
var pos = entity.Get<Position>();  // 抛异常或返回脏数据

// ✅ 正确：检查 IsAlive
if (entity.IsAlive())
{
    var pos = entity.Get<Position>();
}
```

### 21.7.2 修改迭代中的 Archetype

```csharp
// ❌ 错误：在 Query 回调中 Add/Remove 组件
_world.Query(in query, (Entity e) =>
{
    e.Add<Dead>();  // 修改 Archetype，破坏迭代
});

// ✅ 正确：用 CommandBuffer 延后执行
var buffer = new CommandBuffer();
_world.Query(in query, (Entity e) =>
{
    buffer.Add(e, new Dead());
});
buffer.Playback(_world);
```

### 21.7.3 跨 World 访问 Entity

```csharp
// ❌ 错误：Entity 与 World 不匹配
var worldA = World.Create();
var worldB = World.Create();
var entity = worldA.Create<Position>();
worldB.Set(entity, new Position());  // WorldId 不匹配，崩溃！

// ✅ 正确：始终通过原 World 访问
worldA.Set(entity, new Position());
```

🔥 `Entity.WorldId` 字段记录了它所属的 World。扩展方法 `entity.Get<T>()` 内部会查 `World.Worlds[entity.WorldId]`（[EntityExtensions.cs#L25](file:///d:/Unity/Arch/Arch/src/Arch/Core/Extensions/EntityExtensions.cs#L25)）——跨 World 访问会引发未定义行为。

### 21.7.4 忘记 `partial` 关键字

使用 Arch.System 源生成器时：

```csharp
// ❌ 错误：类不是 partial，源生成器无法注入
public class MovementSystem : BaseSystem<World, float> { }

// ✅ 正确：加 partial
public partial class MovementSystem : BaseSystem<World, float> { }
```

### 21.7.5 使用 PURE_ECS 时忘了 WorldId

在 `PURE_ECS` 模式下 Entity 没有 `WorldId` 字段，扩展方法不可用：

```csharp
#if PURE_ECS
// ❌ 这些扩展不可用
entity.Get<Position>();
entity.Set<Position>(new Position());
#endif

// ✅ 必须显式通过 World 访问
world.Get<Position>(entity);
world.Set(entity, new Position());
```

📖 详见 [第13章 PureECS](13-PureECS与性能优化.md)。

### 21.8.2 编写自己的基准测试

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]
public class MyBenchmark
{
    private World _world;
    private QueryDescription _query;

    [IterationSetup]
    public void Setup()
    {
        _world = World.Create();
        _query = new QueryDescription().WithAll<Position, Velocity>();
        for (int i = 0; i < 1_000_000; i++)
        {
            _world.Create(new Position(), new Velocity());
        }
    }

    [IterationCleanup]
    public void Cleanup() => _world.Dispose();

    [Benchmark]
    public void Query_Lambda()
    {
        _world.Query(in _query, (ref Position p, ref Velocity v) =>
        {
            p.X += v.X;
        });
    }

    [Benchmark]
    public void Query_IForEach()
    {
        _world.InlineQuery<MoveJob>(in _query);
    }
}

public struct MoveJob : IForEach
{
    public void Update(Entity e) { /* ... */ }
}

// 入口
BenchmarkRunner.Run<MyBenchmark>();
```

💡 使用 `[MemoryDiagnoser]` 可以看到 GC 分配字节数——这是判断是否产生闭包的利器。

### 21.8.3 Unity Profiler 集成

在 Unity 中可以用 `Profiler.BeginSample` 标注 Arch 调用：

```csharp
using UnityEngine.Profiling;

private void Update()
{
    Profiler.BeginSample("Arch.Movement");
    _world.Query(in _moveQuery, (ref Position p, ref Velocity v) =>
    {
        p.X += v.X;
    });
    Profiler.EndSample();
}
```

🔥 在 Profiler 窗口可以直观看到每个 Query 的耗时与 GC Alloc。

### 21.8.4 常见性能瓶颈速查

| 症状 | 可能原因 | 排查方法 |
|------|---------|---------|
| FPS 帧率低 | Lambda 闭包分配 | Profiler 看 GC Alloc |
| 实体数变多卡顿 | Chunk 扩容频繁 | 调大 `entityCapacity` |
| 多线程反而更慢 | 任务太碎、调度开销大 | 用 `ParallelQuery` 而非自己 new Thread |
| 内存增长不止 | World 未 Dispose | 检查 OnApplicationQuit |
| Editor 卡顿 | GetAllComponents 频繁调用 | 关闭调试 HUD |

## 21.9 配套示例

本章的配套 Unity 示例代码位于 `Assets/Scripts/Chapter21/BestPracticeDemo.cs`，包含：

- 一个**错误示范**脚本（演示所有陷阱）
- 一个**正确实现**脚本（最佳实践）
- 一个 Benchmark 入口（在 Editor 中可运行）
- 一个 Profiler 标注辅助类

运行后效果：

1. 在 Editor 顶部显示 FPS 与 GC Alloc
2. 对比错误示范与最佳实践的耗时差异
3. Profiler 中可定位到每个 Query 的开销

```csharp
// Assets/Scripts/Chapter21/BestPracticeDemo.cs 摘录
public class BestPracticeDemo : MonoBehaviour
{
    private World _world;
    private static readonly QueryDescription _query =
        new QueryDescription().WithAll<Position, Velocity>();

    private void Awake()
    {
        _world = World.Create(entityCapacity: 10000);
        for (int i = 0; i < 10000; i++)
        {
            _world.Create(
                new Position { X = i },
                new Velocity { X = 1 });
        }
    }

    private void Update()
    {
        Profiler.BeginSample("Arch.Update");
        _world.Query(in _query, (ref Position p, ref Velocity v) =>
        {
            p.X += v.X;
        });
        Profiler.EndSample();
    }

    private void OnApplicationQuit() => _world?.Dispose();
}
```

## 本章小结

| 主题 | 核心要点 |
|------|---------|
| 组件设计 | struct 而非 class，小而专注，避免引用字段，用 record struct |
| 系统设计 | 单一职责，无状态，复用 SharedJobScheduler |
| 查询优化 | 缓存 QueryDescription，用 IForEach 内联，合理 WithNone |
| 内存管理 | World 必须 Dispose，回调中别创建 World，警惕闭包 |
| 线程安全 | 结构变更单线程，并行查询用 CommandBuffer |
| 基准测试 | 用 Arch.Benchmarks + Profiler 双管齐下 |

下一章我们将深入讨论**调试技巧与工具**，帮助你在出问题时快速定位。
